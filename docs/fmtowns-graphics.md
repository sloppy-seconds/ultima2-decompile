# The FM Towns graphics — format, the crosswalk, and three refutations

Scope: what `references/fmtowns/` holds, how its art decodes, and the DOS
`art index -> FM Towns tile` crosswalk in `disasm/fmtowns-crosswalk.tsv`.

Grades per `AGENTS.md` § 5. Media: `references/fmtowns/`, the owner's rip of
*Ultima Trilogy 1-3 (1990)(Origins)(Jp-En)* — a `.img` plus `.ccd`/`.cue`.
Tooling: `tools/fmtowns_xwalk.py`. Owner mapping sessions: 2026-11-04.

> **Read this before trusting any earlier statement about these files.** Three
> claims that were made in this project or inherited from the sibling
> `fm-family-ultima-trilogy` docs turned out to be wrong, and two of them were
> load-bearing. They are § 5, § 6 and § 7.

---

## 1. The disc reads with no dependencies

`*.img` is an ISO-9660 volume on **raw MODE1/2352 sectors**, so `7z` refuses it.
A ~90-line reader (PVD at sector 16, strip the 16-byte header and 276-byte ECC
per sector, walk directory records) extracts all 62 `GRAPH/*.TIF`. Verified
byte-identical to the sibling project's independent extraction.

The volume has real directories — `GRAPH/`, `SOUND/`, `UT1/`, `UT2/`, `UT3/`.
That matters in § 8.

## 2. The tile format

Every bank is **512 header bytes + 64 tiles of 512 bytes**. A tile is **32x32,
4bpp packed, high nibble = left pixel**. Only indices **0..7 occur** — measured
zero nibbles above 7 across 196,608 nibbles in each of six banks. It is
8-colour art sitting in a 4-bit field.

`PLAYER` and `EXTRA` carry a real TIFF IFD with `StripOffsets=512`. `ENEMY2`,
`CHEST`, `DUNG1`, `DUNG2` and the `MAP2_*` files have no TIFF magic but the same
512-byte dead prefix, which shows up as a first tile with 2 non-zero pixels.

What the banks hold, as far as it is known:

| bank | contents |
| --- | --- |
| `MAP2_1` / `MAP2_2` / `MAP2_3` | per-planet overworld terrain, walls, borders, and **A-Z at tiles 38..63** |
| `EXTRA` | objects — ships 16..19, horses 20..24, trees, buildings, effects |
| `ENEMY2` | creatures |
| `PLAYER` | avatar, varies by race and class |
| `CHEST`, `DUNG1`, `DUNG2` | dungeon |

Animation frames are **adjacent**, stride 1. See § 7.

## 3. The palette

Not in any asset file, and not a static table in the executable: `EGB_palette`
at `0x103c84` in `ENCHANT.EXP` is a setter that stores a far pointer out of
`[edi+8]`, so the table is assembled at run time. The in-game table read from the
running machine is what `tools/fmtowns_xwalk.py` uses for indices 0..7:

```
000000 0000FF FF0000 000000 00FF00 00FFFF FFFF00 FFFFFF
```

Two things about it surprise people. **Index 3 is black**, a duplicate of 0, and
that is not a placeholder — the letter tiles use exactly indices `{3,7}`, which
is black on white, and that is what the letters look like in a real screenshot.
And only 0..7 are ever used, so the upper plane is dead for this art.

Unproven: whether the title, town, dungeon or combat screens install a different
table. The clean measurement is to break on `EGB_palette` and dump the 512 bytes
behind `[edi+8]`.

## 4. The crosswalk

`disasm/fmtowns-crosswalk.tsv`, generated by `--export`, gated by `--check`.
64 rows: 39 named by the owner, 25 derived. Columns are
`art_index, fm_tiles, count, source, description`.

The mapping is **set-valued**, because one DOS tile is usually a run of FM tiles
(animation frames and variants). A tile appearing in more than one row is a
deliberate collapse, not an error: `MAP2_1/37` serves `1F`, `3A` and `3B`, which
are all banner frame rules.

Derived, not hand-named:

* **25 letters.** The DOS font rows carry their glyph in `disasm/tile-art.tsv`,
  and `MAP2_1` tiles 38..63 are A..Z in order. Structural, and the gate re-derives
  it: `--check` fails if a letter row disagrees with the rule.
* **10 creatures.** DOS art names in `bestiary/bestiary.tsv` (third-party names
  attached by bitmap identity) joined by name to the Codex FM frames already in
  `bestiary/cache/frames/fm-towns/`, then located by silhouette. Graded by the
  gap to the runner-up, because a humanoid that beats the next humanoid by 0.01
  is the *name* doing the work, not the shape.

**All 10 derived creature candidates were confirmed by the owner**, each extended
by its adjacent partner — including the two graded `thin` and `weak`. That is the
strongest validation this approach has.

Not derivable, measured as a negative: **terrain**. Structural matching of DOS
tiles to FM tiles gives margins of 0.00-0.03 across every terrain, object and
block row, so the best candidate is never separable from the runner-up. Terrain
has to be named by a person. The one high-margin hit was degenerate — a
near-uniform FM tile matching three different near-empty DOS tiles at once.

### Parked

1. **Dungeon and tower art** — `CHEST`, `DUNG1`, `DUNG2` decode and are available,
   nothing is mapped.
2. **`PLAYER` avatar art** — the whole bank is unmapped. FM Towns varies the avatar
   by race and class, which is an axis the single DOS atlas does not have, so this
   is not just more rows.
3. **Horse and boat directional variants.** The owner reports facing variants; the
   rows currently carry the animation pair only.
4. **`MAP2_2` planet-2 terrain** — the 15 per-planet tiles.

## 5. Refutation: `MAP2_*` is art, not map data

Inherited claim, from the sibling project's `map-geometry.md`: `MAP2_1` is a
256x128 map buffer, and the region shared by all three files is a shared map body.

**Wrong.** `MAP2_1` tiles **38..63 are the letters A through Z**, white on black,
in order, byte-identical in all three files. That shared letter block is exactly
the "rows 29-56 identical across all three" that was read as a shared map body.
The three files are per-planet tile banks.

Comparing them tile by tile: **49 of 64 tiles are byte-identical across all
three**; only 15 differ — tiles 1-2, 4-6, 7-11, 13-16 and 35. `tools/`
re-measures this on every build and refuses to emit the page if the recorded
lists drift, because a hand-copied version of this list was wrong twice in one
sitting.

Tile 16 is the interesting one: `MAP2_2/16` and `MAP2_3/16` are byte-identical
and `MAP2_1/16` is not. The owner identified these as **moongate on planet 1,
shield on planets 2 and 3**, which is the one place the three planets disagree
about what a slot means.

## 6. Refutation: the palette I first used

An earlier version of `tools/fmtowns_xwalk.py` rendered the banks in EGA-bright
order on the strength of reading the letter tiles as cyan-on-white. That was a
misread of `00FCFC` as `00FFFF` — FM Towns is 6 bits per channel — and it made
every bank look like dithered noise. The machine's own table (§ 3) is correct and
the art proves it: grass, water, brick, ships, horses and the alphabet all read
properly with it.

Related, and worth keeping straight: the **Codex FM Towns GIFs are cleaned
redraws, not raw rips**. `FMOrc.gif` is 32x32, 2 frames, 7 flat colours, no
dither; aligning it to the matching decoded tile gives per-index purity of only
0.34-0.55, so the correspondence is not even a function. They are good for
"is this the same creature" and useless for "what colour is it". The real
screenshots show the game genuinely dithered, same character as our render.

## 7. Refutation: the animation stride is 1, not 2

Stated in this project's chat and in an early tool docstring: the frame stride is
2. That came from a mean agreement over all candidate pairs, which measured how
much tiles look alike rather than what the frame order is.

The owner's own identified pairs refute it directly — adjacent agreement beats
the best stride-2 partner in six of seven cases, by wide margins:

```
EXTRA/3+4      adjacent 0.99   best stride-2 0.13
EXTRA/1+2      adjacent 0.97   best stride-2 0.15
ENEMY2/40+41   adjacent 0.93   best stride-2 0.20
ENEMY2/16+17   adjacent 0.82   best stride-2 0.38
```

Re-measure on **identified** pairs before trusting a statistic of this kind.

## 8. The forcefield row, and why the CD never lost a planet

Art `17` is a forcefield. The true FM identification is `MAP2_3/35`, but the
table maps it to **`MAP2_1/34`** so the whole crosswalk resolves against a single
planet-1 atlas. `MAP2_1/34` is byte-identical across all three banks and shares
the DOS tile's vertical-bar structure; `MAP2_1/35` is terrain. The trade-off is
recorded in the TSV header: the table says "closest Earth-bank equivalent" for
this one row, not "the tile the game uses".

Worth noting against the owner's recollection, because the bytes disagree: art
`0x17` **does** occur on Earth in the DOS game — 72 cells in `mapx03`, a tens-0
sector, and 4 in `mapx71`. So the content difference is in the port: the FM Towns
version carries the forcefield art only in its planet-3 bank.

That connects to a bigger point. The DOS loss of the outer planets was a filename
collision — MS-DOS had no directories, so `MAPG10` and `mapx10` were the same name
and the floppy-to-CD folder merge kept Earth's. See
`docs/planet-maps-galaxy-patch.md`. **The FM Towns disc is a directory-based ISO
and has no mechanism to suffer that bug**, and `UT2/MAP.MP2` is exactly
41 x 4096 bytes, where 41 = the 33 sector filenames in our merged DOS folder
plus the 8 that collided. That makes it a candidate independent source for the 8
real planet maps, which today exist only in the fan patch. Decoding `MAP.MP2`'s
cell encoding is unpicked work.

## 9. Reproducing

```bash
python3 tools/tile_atlas.py --out tmp/tiles          # DOS tiles, needs original/
python3 tools/fmtowns_xwalk.py --serve              # the drag-and-drop editor on :8098
python3 tools/fmtowns_xwalk.py --export OWNER.json disasm/fmtowns-crosswalk.tsv
python3 tools/fmtowns_xwalk.py --check disasm/fmtowns-crosswalk.tsv
```

`--check` is wired into `tools/check_all.sh`. Its controls — a dropped row, a
broken letter mapping, an unknown bank — were all run and confirmed red before
the passing run was believed.

The editor keeps verdicts in browser `localStorage` and exports TSV or JSON.
Right-click marks "no equivalent". Derived candidates appear as a dashed ghost
showing the actual tile, colour-coded by confidence.
