## 3. ⚠️ The CP5 gate: my alarm was overstated, but there IS a real defect

Last turn I flagged `CP5 SPEC: PASS` as untrustworthy because the behavioural line reported
**0 checks**. **That alarm was wrong in its severity and I want that on the record** — see
below. There is still a genuine, narrower bug.

`engine/tests/run_cp5.sh:105`:

```sh
ok "CP5 spec: C1/C2/C6 behaviour ($(grep -c '  ok  ' "$WORK/combat.out") checks, $(tail -1 "$WORK/combat.out"))"
```

`combat_check.c`'s `CHECK` macro **prints only on failure**:

```c
#define CHECK(cond, ...) do { checks++; if (!(cond)) { fails++; \
    printf("  FAIL  " __VA_ARGS__); printf("\n"); } } while (0)
```

So `grep -c '  ok  '` is **structurally always 0**. Verified directly:

```
exit=0
grep -c '  ok  ' = 0
tail: combat_check: 4066 checks, 0 failures
```

**What is true:** the behavioural run really does execute 4066 checks against the real
`src/game/combat.c`, and `run_cp5.sh` tests its **exit code** (`elif "$WORK/combat_check"
… then ok … else bad`), so a genuine failure **does** go red. The gate is not toothless.

**What is wrong:** the reported check count is a meaningless number that will always read 0.
The defect that matters is the one it *masks*: if the behavioural run ever silently executed
**zero** checks — every test function becoming a no-op, a `main` that stopped calling them,
a link that pulled in stubs — the line would still print `0 checks` and still say PASS, and
the `0` would look like the known cosmetic quirk rather than a catastrophe.

**The fix, and it is small:** parse the real count from the summary line and assert it is
non-zero.

```sh
n=$(sed -n 's/^combat_check: \([0-9]\+\) checks.*/\1/p' "$WORK/combat.out")
[ "${n:-0}" -gt 0 ] || bad "CP5 behavioural run executed 0 checks — the spec is not running"
```

**Demonstrate it failing before trusting it**, per `AGENTS.md`: break one test call in
`main`, confirm red, restore. And note the same script already has one fixed instance of
this class of bug on record (it used to `exit 0` unconditionally while `combat.c` was
absent) — this is the second occurrence in the same file, so look for a third.

## 5. Architectural consequence of "no leaves-combat state"

Recorded in `docs/phase4-state.md` § CP5 as a second standing design constraint. Three
consequences:

* **It corroborates C3.** With no separate combat mode, paralysis being a *movement
  rejection* is not a quirk to emulate, it is the only shape that makes sense — a paralysed
  step takes the same reject path as walking into a mountain. One movement system, not two.
* **Any battle screen or combat-mode flag added later is a deviation**, not a feature.
* **It collapses persistence to one question: the save.** See G24.

## 6. Open threads worth pulling, with the lead already found

### The aggro marker — the owner's hunch has a concrete candidate

`DS:1D7` is the sixth `monx` array, values `01..03` and `81..85`, and `docs/monster-spawn.md`
says *"no consumer of `DS:1D7` has been named"* beyond one writer.

**That is now out of date — there is a reader.** `asm/40C0` (inside the merged
`asm/4050_cmd_T.asm`):

```asm
mov    0x1d7(%di),%al
cmp    $0x80,%al
jb     L_0042cb
```

It tests **bit 7**. A high-bit flag alongside a low group value is exactly what an
aggro/awake marker looks like. **Do not promote this to a conclusion** — it is in the
TRANSACT path, not the combat path, and a reader that branches on bit 7 is not proof of
meaning. But it is the thread, and `docs/monster-spawn.md` should be corrected to name
`asm/40C0` as the first consumer.

index** `[DI+0x1B7]`), and the spell/steal paths are already named (`3139_cast_spell_flow`,
`3F5D_steal_attempt`). A static look for a shared "infamy"/hostility byte is cheap.

## 7. Corrections I made to myself this session — read so you don't repeat them

* **`popcount` → bit length** in `asm/20AB`'s loop count.
* **"multiply by repeated addition" → Fibonacci-style BCD walk** seeded 4,4.
* **A simulator whose `DAA` subtracted 6 instead of adding** produced plausible nonsense.
* **`DS:19/1A` is the delta, then "is not the delta", then "is the delta"** — the middle
  retraction over-corrected. The lesson is that one sample after one action is not a
  measurement; the `(1,1)` reading only became meaningful after all four directions and
  five movement keys agreed.
* **"0 checks means the gate cannot go red" was overstated** — the exit code is checked.
  The real defect is the meaningless count. See § 3.
* **`FUNNY, NO RESPONSE!`** is a delivered-and-refused verdict, not a dropped key. My
  opposite reading cost a whole sweep.
* **`0x68`/`0x7C` are map cell values; `0x6C` is a creature type byte.** Conflating them
  caused a wrong claim about the Merchant.
