## Standing traps, unchanged and still true

* **Memory reads pause the CPU**; keys sent into that window are silently lost. Settle
  0.5–1 s after a read before injecting a key, and verify every step.
* **`monitor breakCsIp` parses hex while `/api/status` reports decimal.** Passing decimal
  arms a trap on an address that can never execute and every later "no reject observed"
  means nothing. `reject_trap.py` converts in one asserted place.
* **`ExecutedInstructions` is a deduplicated address set, not a trace** — it cannot count
  per-step events. `blocks` are *discovered*, not executed; the authority for "this ran"
  is `ExecutedInstructions` inside `spice86dumpExecutionFlow.json`.
* **`DS:20` is scratch, not a reject signal.** `state.h` says so; `turn_recorder.py` was
  violating it and now emits `stalled` with cause unresolved.
* **Never edit a file with a script; never heredoc a non-trivial script.** `str.replace`
  that misses returns the string unchanged and exits 0.
* **In `asm/`, only the filename and `#` lines may change — labels are body.** CP0 md5s
  every non-`#` line.
* **Demonstrate a gate failing before trusting it passing.**
* **`pgrep`/`pkill -f` matches its own shell.** Kill by pid, or check ports.
* **Scratch goes to `/var/tmp`, never `/tmp`** (tmpfs here — it takes RAM from the model).
* **Probe maps must be installed before launch** (`spice86_start.sh --seed-map`); the game
  reads `mapxNN` at startup.
* **The world wraps.** A scripted walk assuming a flat grid desynchronises near an edge;
  start probe walks mid-map (`u2_mkprobe.py --start-x`).
* **Enumerate `captures/spice86/` before running a new capture.** Sixty-plus dumps were
  already on disk and one of them contradicted a conclusion drawn from a fresh run.
  `tools/monster_record_scan.py` makes that check one command. AGENTS.md says this; it was
  still ignored, and the cost was a wrong commit plus an over-correcting one.
* **Read the tool index in `docs/spice86-capture.md` before writing anything against a
  live session.** `send_keyboard_key` has been in Spice86's MCP surface the whole time;
  a BIOS typeahead-ring poke was written and deleted before anyone looked.
* **`[DI+0x1B7]` is a kind index, not a sprite.** `docs/spice86-live-findings.md` calls it
  "monster sprite stamped into the map cell" and that is wrong. It briefly made a transform
  look corroborated twice over when it was one field relabelled. Trust the live dump.
* **A single area is not a sample.** The sector-0 compound reads HP 255 for everything;
  ordinary wandering spawns match the base exactly. Concluding from one location is what
  turned a correct finding into a retraction and back again.
* **A capture directory name is not a fact about its contents.** `airport32` is not an
  airport and there is no airport mode — the game has plane and rocket *tiles* (`mapx03`
  depot; plane is map byte `0x4C`, art `0x13`; landing gated to grass `0x08`). That dump's
  4 KB grid is byte-identical to `dungeon-35-live`'s, so it is a dungeon. Names were chosen
  by whatever session was hunting at the time. Check the bytes before narrating a capture.
* **An "active slot" filter is a claim about the encoding.** `type not in (0, 0x40)` is
  correct for the overworld and meaningless in a dungeon, where the field holds `0x01`/`0x02`.
  That filter is what made two encodings look like one broken grid.
* **Look up `DS:0x1800` before re-deriving it.** The 64x64 sector buffer was documented
  twice — `spice86-live-findings.md:85` and `phase4-overnight-cp5-report.md:393`. A fresh
  full-dump scan "found" it a third time. The lookup is a `grep`.
* **Do not upgrade an arithmetic fit into a mechanism.** `type >> 2` matching an art index
  is not evidence that code shifts by 2. This happened twice in one day in the same
  sentence, once as "corroborated 8/8" and once as "the arms mask with `0xFC` and shift
  `>>2`" — the arms do neither. Check the instruction bytes before describing what code
  does.
* **`view.h`'s two-step is not a bug.** `u2_view_index` then `u2_view_art` composes to
  exactly `>>2`. It has been ticketed as a defect across two handoffs because the ticket
  quoted line 54 in isolation instead of reading lines 78–94.
